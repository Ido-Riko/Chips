# Japanese practice and drawing sketchbook

Implemented on 13 November 2026 under the M4 local-first rule. These integrations do not complete M4 or the separate M3 voice service. Drawing server deployment and real vision-model acceptance remain pending while `chips-server` is offline.

## Japanese

Today → Japanese → Study opens a bundled, offline deck of 30 beginner kanji. Recall the meaning/reading, reveal the answer, then choose Again, Got it or Easy. Meanings, kun/on readings and stroke counts come from KANJIDIC2 through [kanjiapi.dev](https://kanjiapi.dev/); no dictionary content is generated by an AI. The selected dataset and in-app attribution retain [EDRDG attribution conditions](https://www.edrdg.org/edrdg/licence.html) and [CC BY-SA 4.0](https://creativecommons.org/licenses/by-sa/4.0/). See `chips-mobile/app/src/main/assets/KANJI_LICENSE.txt`.

There are up to three new cards per local calendar day, after due reviews. Again returns after ten minutes and resets the interval step. Got it advances through 1, 3, 7, 14, 30 and 60 days; Easy advances an extra step. Day-based reviews become due at local midnight in the phone's current zone, accounting for DST. This is a simple self-rated review schedule, not FSRS or a claim of mastery. The initial deck does not include example sentences, stroke animations, handwriting recognition or external study-service sync.

Review progress survives restart in SQLite. Reset review progress requires confirmation and keeps existing activity history. The first completed review of a day creates one stable Japanese activity ID in the same SQLite transaction; further reviews do not create duplicate daily completions. The schedule stays local; the resulting activity can use normal optional M2 sync.

## Drawing

Today → Open sketchbook opens the local gallery. Enter an optional practice goal, then Add drawing using Android's photo picker. CHIPS immediately copies the image into private persistent storage and makes a thumbnail, without requiring enrollment or a server. Photos are oriented using EXIF, flattened onto white and normalized to a JPEG up to 1600 pixels on its longest side; this is a practice/analysis copy, not an original-resolution archival backup. Input is bounded to 20 MiB. Notes can be edited locally. Each saved drawing creates one stable Drawing activity independently of analysis success.

Tap a gallery card to view its image, notes, status and retained AI feedback. Send for feedback durably queues upload followed by analysis using the saved HTTPS device enrollment. An unavailable server does not block local saving or Japanese/Beat Saber. Upload/analysis states are distinct. Network failure before establishing server identity is retried with WorkManager backoff; provider/individual-request errors remain visible for an explicit retry. Retry now replaces a waiting request. Disconnect pauses server operations; reconnecting or opening the app reschedules queued work. Repeated completed analysis requests return saved feedback instead of calling the model again. A crash after a provider processed a request but before commit can still require another inference; exactly-once provider execution is not promised.

Remote identity is checked using the existing `/device` contract and bound to the app database. A queued item records its original service/owner/device identity before the first mutation; it cannot silently move to another enrollment. Successful server feedback/model and newly learned status stay available offline. The dashboard shows a short excerpt from actual saved feedback when available. Notes remain local; the image and original practice goal are sent to the server.

Deleting a drawing removes its local image, thumbnail, notes and feedback, and queues removal of any server copy. A never-sent drawing needs no remote cleanup. A late response cannot clear the deletion queue or restore the image. Remote tombstones block delayed retries from recreating deleted IDs. Remote cleanup remains visible/retryable while offline. Deleting a drawing keeps its completed activity history; activities can be managed separately in History.

## Server storage and API

Apply additive migration `003_drawings.sql` using `python -m app.scripts.migrate`; install updated requirements. Drawing image bytes are retained in PostgreSQL `BYTEA` together with owner-scoped metadata, goal, captured date and feedback. Normal database backups therefore include the image copy. This update does not replace existing activity/voice data or introduce a public image URL. All routes use the existing enrolled-device authentication and HTTPS requirement.

| Route | Behavior |
| --- | --- |
| `PUT /api/v1/drawings/{uuid}` | Multipart `image` (JPEG up to 5 MiB/4096 pixels per side), `goal` (up to 2000 characters), `created_at` (captured Unix milliseconds). Immutable ID/content/date; identical retry is idempotent, conflict 409, tombstoned ID 410. |
| `GET /api/v1/drawings` | Latest 200 active metadata records for this owner. |
| `GET /api/v1/drawings/{uuid}` | Retained metadata/feedback. |
| `GET /api/v1/drawings/{uuid}/image` | Authenticated JPEG with private/no-store response headers. |
| `POST /api/v1/drawings/{uuid}/analyze` | Uses the saved image/goal. Saves successful feedback/model/time and returns cached success on retry. A failed/unconfigured model leaves the image untouched. |
| `DELETE /api/v1/drawings/{uuid}` | Clears image, notes/goal and generated feedback, retaining only a minimal tombstone. Also accepts an unseen ID to prevent a delayed upload. |

Server gallery restore/synchronization across phones is not wired into Android yet; these reads support inspection and later recovery. The phone keeps its own working copy. As with any retained database data, old backup retention is managed by the server operator.

## Configure real vision analysis

Drawing vision is configured independently of the deferred M3 voice service. There is no automatic cloud-provider fallback and no fabricated feedback. Set an explicitly selected vision-capable runtime in the server's private `.env`, for example an installed local Ollama vision model using its [documented image-input chat endpoint](https://docs.ollama.com/api/openai-compatibility#v1chatcompletions-with-vision-example):

```dotenv
DRAWING_VISION_URL=http://127.0.0.1:11434/v1/chat/completions
DRAWING_VISION_MODEL=your-installed-vision-model
# DRAWING_VISION_API_KEY=only-if-required-by-your-runtime
```

The URL is the complete chat-completions endpoint. A compatible runtime must accept `image_url` with an inline JPEG data URL and return `choices[0].message.content`. The request includes a bounded drawing-tutor prompt asking for observed strengths, two improvements and a concrete next drill. Responses are bounded, request timeouts are finite, and redirects are not followed. Choose the model deliberately and validate it with a real drawing before claiming AI quality. Server keys never enter Android.

After configuration, restart the service, upload a real drawing from the phone, confirm image retention and real feedback/drill, repeat the request, restart the app and test failed-provider retry plus offline deletion/reconnect cleanup. These real-server/model and physical-phone interaction gates remain open; mock-provider protocol tests do not establish model quality.
